# External feedback, 2026-10-15

A user tried the plugin on their own development: a message-passing
process calculus with a structural congruence, observed through barbs,
written in the usual `Section`/`Context` style. Their write-up is at the
end, verbatim. This note is what we made of it on 2026-10-19, at `main`
`41db89c` (the feedback was at `83f8555`; nothing between the two touches
what it reports, apart from `Bounds Memory`, below).

Each item has a minimal case in `test/rocq/Test.v`, section
`ExternalFeedback` (and `ParameterisedLTS` for item 2). The open ones are
indexed in `OUTSTANDING.md`.

## What we found

| item | verdict | status |
|---|---|---|
| 1. left-recursive congruence rule runs away | **bug**, reproduced | open |
| 2. `Section` + `Context` parameters | limit, known; a cheaper workaround found | workaround documented |
| 3. premise through a `match` on an unknown | limit, reproduced | pinned; supported forms documented |
| 4. proofs do not close for different-but-bisimilar terms | **bug**: a related crash reproduced, not the loop itself | open |
| 5a. no message on a successful `Run` | fixed | `Notice` on every `Run` |
| 5b. under `Fail`, the reason is hidden | fixed in part | `Run Bisim`'s error is now a sentence |
| 5c. JSON output too large | fixed | plain text by default; `Format`, `Detail` |

### 1. A step rule whose premise is the relation itself

Reproduced with a four-constructor calculus: `cong` reflexive and
symmetric, and

```coq
| r_str p p' q q' l :
    cong p p' -> cong q q' -> step_rec p l q -> step_rec p' l q'
```

`MeBi Run LTS (pre a done) Using step_rec` passed 2GB in 12s and was
killed by the cap. The cause is as the feedback guessed. Extraction
explores an LTS premise by recursing into `check_valid_constructors`
(`handle_app` in `lib/rocq_tools/rocq_monad_utils.ml`), with no depth
bound and no record of the premises it is already exploring. `cong` is
reflexive, so `step_rec p'` asks for `step_rec p'` again. `Premise Depth`
bounds only the other premises. `Bounds Memory` (added 2026-10-16, after
the feedback's build) does not catch it either: it is checked between
states (`src/graph_builder.ml`), and this happens inside one.

The fix the feedback suggests is the right shape: notice the repeat, or
bound the recursion, and end in `LTS_Incomplete`, which already explains
itself. Not done yet. The reproducer is in a comment in `ExternalFeedback`,
since a test of it today would only eat memory.

### 2. `Section` parameters

Known (`doc/limitations.md`, "LTSs with parameters"; pinned
`ParameterisedLTS`). The documented workaround restates the relation in a
module, which for the feedback's calculus was ~25 constructors and an
equivalence proof. A one-constructor wrapper does the same job:

```coq
Inductive wrapped3 : nat -> option unit -> nat -> Prop :=
| wrap3 n l m : countLTS 3 n l m -> wrapped3 n l m.
```

MeBi does not explore `countLTS 3` as an LTS. It decides the premise with
its proof search, which enumerates the target. Extraction and a proof both
work (`ParameterisedLTS.wrapped3`). The cost: derivations deeper than
`Premise Depth` (default 16) need it raised. Not yet tried on a relation
with a congruence rule, where the bounded search might also sidestep
item 1.

### 3. A `match` on an unknown argument

Reproduced: `barb p x := match x with a => ... | b => ... end`, with `x`
fixed by nothing, is `LTS_Incomplete`. A `match` on the source term works,
and so does `In x (barbs_of p)` with `barbs_of` computable. Enumerating the
constructors of a matched unknown would be a new *capability*; the README
now says which forms work.

The second warning in that case says "`[sink]` still has an unknown in
it". The unknown is in the label (`Barb ?x`), not the target. A wording
bug, small.

### 4. Proofs that do not close

Not reproduced as reported (constant open goals, context growing by two
hypotheses a step). An unused record field alone is not the cause: a
record-valued calculus, with and without a layered barb relation, closes
in 74 and 186 steps.

What did reproduce is a crash in the same shape, a congruence premise in
front of a step premise (item 1's workaround). With

```coq
| s_str p p' q q' l : cong p p' -> cong q q' -> base p l q -> step p' l q'
```

`Run Bisim` says `loop` and `par loop done` are bisimilar, but the proof
fails at step 13 with "Tried to normalize ill-typed term", under both
cofix strategies. The goal focused at step 12 is `base ?p None ?q`: the
solver has applied `s_str` without fixing its source. A proof of `loop`
against itself closes. Pinned as a known-wrong `Fail` in
`ExternalFeedback`. Whether the feedback's loop and this crash are one
bug is not known. Their semantics would settle it.

The feedback also noticed `Auto` take the nested cofix for a
`weak_bisimilar` goal, where the README said it would take the mutual
one. The README was wrong: `Auto` costs both and takes the cheaper.
Corrected.

### 5. Output

- **`Notice` on success.** Every `Run` command now ends with one: the term
  and the sizes for `LTS`, `FSM`, `Saturate`, `Minimize` and `Merge`, the
  verdict for `Bisim` and `Sim`.
- **`Fail`.** `Run Bisim` failed with the bare word `Not_Bisimilar`. It now
  names the two terms and the class count, as `Run Sim` already did, and
  with `FailIf NotBisimilar False` it is a warning instead of silence.
  `rocq compile` prints no `Fail` message at all, so a test that must show
  its reason can set `FailIf NotBisimilar False` and read the warning.
- **Size of `Result`.** Done 2026-10-19: results print as plain text by
  default (states, labels, then `from -label-> to`), with `MeBi Config
  Output Format JSON` for JSON and `Output "Detail"` for the derivation
  trees and constructors (README, "Configuration"). In a 3-state FSM's JSON,
  135 of 180 lines had been constructor metadata.

## What worked, by their account

Fast verdicts, correct on every case they cross-checked with their own
checker. Diagnostics that name the fix. Layered relations in `Using`.
From `theories/`: the split between `mutual_sim` and `weak_bisimilar`
showed them their own definition was the coarser one, and
`Hiding.relabel_*` and `Transfer.*` were reused directly.

## The feedback, verbatim

> Written to be read without this repository. Plugin version: `rocq-mebi`
> dev at `83f8555` (2026-10-15), Rocq 9.2.0, OCaml 5.4.1, dune 3.23.

### Setting

The task: given two terms of a small message-passing process calculus
(a reduction-style semantics with a structural-congruence rule, parameterised
by an environment value and a latency constant), decide weak (bi)similarity,
observing terms through a "barb" predicate. The semantics is written in the
usual Rocq style: one `Section` with `Context (D : env) (L : nat)`, a few
`Inductive` relations (one of them the top-level step relation, with the
label split into two arguments), and a congruence relation used inside one
of the step rules.

What I did: restated the step relation as a parameter-free ternary relation
inside a functor (proved equal to the original), layered a second relation
over it that turns barbs into visible steps to a stuck sink state, and ran
`MeBi Run LTS` / `Run Bisim` / `Run Sim` on terms of up to about six states.
Everything below comes from that one project and small systems; I have not
tried to minimise any of it into a standalone repro unless stated.

### Summary

| | |
|---|---|
| Verdicts (`Run Bisim`, `Run Sim`) | fast, and correct on every case I cross-checked |
| Extraction when the step relation contains a left-recursive congruence rule | does not terminate; memory climbs to GBs; no bound contains it |
| Relation defined in a `Section` with `Context` | refused (clear error); workaround costs a functor and an equivalence proof |
| Premise through a `match`-defined predicate with an unknown argument | cannot enumerate; needs a hand-written computable counterpart |
| Proofs (`... As n.` + `Sim Solve k`) for two *different* but bisimilar terms | did not converge in my case, though the verdict was instant |

### What worked well

- **Verdicts are cheap.** A 3-state pair: 0.8 s wall, 412 MB, which is the
  same as loading the file with no commands (0.8 s, 414 MB). A negative
  verdict on 5- and 6-state FSMs: 1.1 s.
- **Diagnostics usually name the problem and the fix.** `LTS_Has_Parameters`
  names the module workaround. `LTS_Incomplete` names the premise that was
  left undecided. The warning shows where a premise was first met, e.g.
  `(structural_congruence ?s21 (Node ...))`, which is how I found the rule
  that was causing trouble.
- **Layered relations in `Using` work**, including with different label
  types per layer, and `Weak As Option <T>` behaved as documented.
- **The shipped theory separates `mutual_sim` from `weak_bisimilar`**, with
  counterexamples in the comments. That is what let me notice that the
  project's own definition was the coarser one; a library that had only one
  "bisim" would have hidden it. `Hiding.relabel_*` and `Transfer.*` were
  directly reusable.
- **The JSON FSM / `Result` output is easy to consume.** I re-decided
  bisimilarity on the extracted FSMs with a separate 100-line checker and it
  agreed on both a positive and a negative case.

### Friction, most impactful first

#### 1. A left-recursive rule runs away silently

The step relation has a rule of the shape

```coq
| Str : forall p p' q q',
    cong p p' -> cong q q' ->
    step p tau q -> step p' tau q'
```

where `cong` is reflexive and symmetric, has constructors that rewrite
`Par x Empty` to `x`, and has *no transitivity constructor*. The conclusion
matches every source term, and the LTS premise is `step` again, on a
congruent copy of the source.

Observed on a system with a single enabled transition:

| Setup | Result |
|---|---|
| `Premise Depth 1`, `Bounds States 60`, `Transitions 400`, `FailIf Incomplete False` | RSS > 3 GB after 77 s (killed by an external watchdog) |
| `Premise Depth 2` / `3` | > 3 GB at 111 s / 2.2 GB at the 120 s cap |
| default depth (16), default bounds | still running at > 10 min, 100% CPU, ~1 GB (stopped by hand) |
| same rule with the recursive premise replaced by a premise over the relation *without* the rule (so applied at most once) | finishes: ~1 s, 420 MB at depth 1-3; 33 s at depth 16 |

So the blow-up is the recursion, not the number of solutions of
`cong p ?p'` (finite for a fixed `p` here), and the state/transition bounds
are not reached because the work happens inside one state's premise
enumeration. Raising bounds does not help. The warning does appear
("whose solutions MeBi may not have found all of ..."), but the run goes on.

This is my reading from the experiments, not from the plugin's code.

**Suggestion:** a recursion-depth or work/time/memory budget for premise
exploration that ends in `LTS_Incomplete` (which already exists and already
explains itself), rather than continuing. Even a cap on the nesting of the
LTS under exploration reached through its own premises would do.

#### 2. `Section` + `Context` parameters

`Context (D : env) (L : nat)` is the normal way to write such a semantics
in Rocq. The plugin's refusal is clear and the README documents the
workaround, but here the workaround meant restating about 25 constructors in
a functor over `(D, L)` and proving the copy equal to the original. `Using`
accepts only a bare reference, so an applied `step D_alive` is a syntax
error and each environment value needs its own module instance.

**Suggestion:** accepting an applied term after `Using` is already sketched
in `doc/limitations.md`; for developments written this way it would remove
most of the porting cost. Failing that, a short worked example for a
`Section`-based development in the README would help.

#### 3. Premises through a `match`-defined predicate

`barb R x` unfolds to `match x, ys with ... => ne_In ... end` over an unknown
`x`. The plugin cannot enumerate `x` and reports `LTS_Incomplete`
("a premise headed by [barb] was left undecided"), plus a second warning that
the transition target "still has an unknown in it". Replacing it with a
computable `barbs_of : term -> list barb` and the premise `In x (barbs_of R)`
worked immediately.

**Suggestion:** when a premise unfolds to a `match` on an unknown
inductive-typed argument, enumerating that argument's constructors (as it
already does for `In`) would cover this. At minimum the README's list of
premise shapes could say that `In x (f t)` with computable `f` is the
supported form.

#### 4. Proofs do not converge for different-but-bisimilar terms

For `Run Bisim x With R And y With R As w.` followed by `Sim Solve k`, with
`x` and `y` bisimilar but syntactically different (they differ only in a
field that has no effect on behaviour), the three-state game did not close:

| `Sim Solve k` | wall | peak RSS | open goals |
|---|---|---|---|
| 32 | 1.3 s | 439 MB | 5 |
| 128 | 7.4 s | 482 MB | 5 |
| 256 | 23 s | 541 MB | 5 |
| 512 | 82 s | 678 MB | 5 |
| 3000 | not finished at 25 min | 1.7 GB | n/a |

The number of open goals is constant, the context grows by about two
hypotheses per step (`H1019` by step 512), and cost per step grows with the
context, giving roughly a x3 time increase per doubling of the bound
(2.6 s at 64, 7.4 s at 128, 23 s at 256, 82 s at 512).

Contrasts, all with the same relations:

- `x` against *itself* (also when written through a different definition
  that unfolds to the same term): the proof closes in 0.8 s.
- `x` and `y` differing only in an unused checkpoint field, or only in a
  clock field: not closed in 300 steps (28 s), verdict instant.
- `MeBi Config Premise Depth` 2 and 4, `Solver Answers Greedy` / `Minimal`:
  no change at bound 128.
- `Solver MutualCofix True`: the message changes to "mutual cofix, as
  configured" and the goal count to 7, still constant at bounds 64, 256, 600.
  Under `Auto` the message said "nested cofix, chosen by Auto", while the
  README says a `weak_bisimilar` proof needs the mutual one.

I did not investigate further (see below), so I do not know whether it is
the layering, record-valued terms, premise refutation, or something else.

**Why it matters:** a verdict that cannot be certified by `Qed` is of limited
use in a theorem-proving development, so for this project the proofs were
the point and the verdicts only a pre-check.

#### 5. Smaller things

- With `Output "Info" False`, a successful `Run Bisim` prints nothing, so
  "bisimilar" is only the absence of `Not_Bisimilar`. A one-line notice
  would help.
- Under `Fail`, the reason is hidden, so confirming that a negative verdict
  failed for the *right* reason meant removing the `Fail`.
- `Output "Result"` / `"DecodeResults"` print very large JSON for small
  systems (thousands of lines for six states); a compact table of
  "classes" would be easier to read.

### What I did not do

I did not minimise 1 or 4 into a standalone repro, did not read the
plugin's source, and did not test failure environments, receive-with-timeout
rules, or recursion. Evaluation scope was this one calculus, systems of up to
about six states, and the fragment of the semantics the plugin could
extract.

### Reproducing the numbers

Wall time and peak RSS were measured with a small wrapper that polls the
RSS of the whole process tree and kills at a limit. All runs were
`rocq compile` of a single file that `Require`s `MEBI.loader`.
